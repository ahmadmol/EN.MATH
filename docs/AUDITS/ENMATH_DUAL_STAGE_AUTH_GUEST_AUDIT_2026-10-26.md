# تدقيق EN.MATH: المرحلتان والدخول والزائر والبيانات

**التاريخ:** 26 أكتوبر 2026 — **الحالة:** تحليل فقط؛ ليس موافقة إطلاق أو بدء تنفيذ.

## 1. النتيجة التنفيذية

يمكن بناء تجربتين بصريتين منفصلتين للتاسع والبكالوريا داخل التطبيق الحالي دون تكرار منطق التعلم والجواهر، وبالاستفادة من العمل الموجود. لكن التطبيق الحالي **ليس تجربتين تعليميتين مكتملتين، وليس نظام حسابات سحابيًا حقيقيًا**.

النسخة المحلية سبقت بعض ملاحظات الخطة: توجد هوية طالب محلية UUID ثابتة المرحلة، وزائر مستقل لكل مرحلة، وحفظ محلي فعلي، وترحيل إضافي للبيانات القديمة مع سجل استئناف، وحماية لمصدر البيانات التالف، ومنع لمصادقة Demo في الإنتاج. يجب الحفاظ على هذه التحسينات وعدم إعادة تنفيذها انطلاقًا من وصف النسخة المنشورة.

الفجوات الحاسمة:

1. التاسع بلا كتالوج دروس أو تدريب؛ Home وStudy يعرضان عدم توفر المحتوى. هذه حالة صادقة وليست تجربة التاسع المطلوبة.
2. المصادقة والتسجيل والتحقق والاستعادة Demo، مع تعطيلها إنتاجيًا؛ إنشاء «ملف طالب محلي» ليس إنشاء حساب موثّق.
3. البكالوريا تستخدم كتالوج Kotlin تجريبيًا به محتوى وتفاعلات فعلية وحفظ حقيقي؛ لا دليل محلي على اكتمال المنهج الرسمي أو اعتماده.
4. عزل المرحلة جزئي: الكتب والتدريب محميان، لكن أمثلة المحلل وبعض مصادر الأسئلة ومتجر الجواهر لا تحمل مرحلة أو إصدار منهج.
5. لا Planner محفوظ أو ترقية زائر إلى حساب أو معالجة تعارض مراحل حساب حقيقي.
6. ترحيل البيانات القديمة يثبت نطاق التخزين والمحفظة القديمة، لكنه يقبل المرحلة التي يختارها المستخدم دون مطابقة معرفات المحتوى معها. يلزم تصميم مراجعة قبل توسيعه.

**التوصية:** تثبيت عقود الهوية/المحتوى والترحيل، واعتماد مواصفات UX للمرحلتين، ثم توسيع المدخل المحلي وربط كتالوج صحيح وتصميمي عرض منفصلين. خدمة الحسابات مشروع لاحق مشروط باعتماد مزود واختباره. لا حاجة لإعادة كتابة التطبيق أو مضاعفة Repositories.

## 3. خريطة التشغيل الفعلية

```text
MainActivity → ENMathApp → LocalDemoRepository + AppViewModel
                        ├─ لا localId ولا جلسة معلم مؤهلة:
                        │    LocalIdentityScreen خارج NavHost
                        │      ├─ اختيار ملف موجود
                        │      ├─ اختيار G9/BAC + إنشاء ملف طالب محلي
                        │      ├─ اختيار G9/BAC + زائر المرحلة
                        │      └─ استيراد قديم مؤكد / مدخل تطوير عند debuggable
                        └─ ملف محلي نشط:
                             استعادة snapshot → main/home
                                  ├─ G9: محتوى غير متاح
                                  └─ BAC: StudentLearningHome → CurriculumScreen

مسارات Splash/Onboarding/Login/Register/Verify/Recovery القديمة باقية في NavHost.
Auth فيها Demo، والمعلم له teacherGraph مستقل باقٍ.
```

الدليل: `MainActivity.kt:10`، `core/navigation/ENMathApp.kt:46,69,76,88,355`، `ProductGraphs.kt:56`.

**أثر مهم:** وجود Splash وOnboarding في الملفات لا يعني أن أول طالب يراهما. شرط المدخل المحلي يعيد من Composable قبل بناء NavHost، لذلك يبدأ المستخدم الجديد حاليًا بملفات التعلم المحلية. الملف المحلي النشط يعاد من التخزين وتوجّه هويته إلى Main. ترتيب Splash مقابل هذا التوجيه يحتاج تحقق جهاز لاحقًا؛ لا نعلن تطابق الرحلة المطلوبة.

### ماذا تعني «المصادقة الحالية» بدقة؟

`AuthViewModel` يصرح بأنه UI demo بلا backend/tokens/إنشاء حقيقي. `validate/beginReset/verify/newPassword` ترفض عندما `demoAllowed=false`. `ENMathApp` وconstructor الإنتاجي للمستودع يشتقان السماح من `FLAG_DEBUGGABLE`؛ حسابات الديمو القديمة لا تُستعاد إنتاجيًا. توجد اختبارات لهذا الحد.

`app/build.gradle.kts` لا يعرّف SDK للمصادقة أو عميل شبكة أو Room/DataStore. Manifest الرئيسي لا يعلن INTERNET. هذا يدعم نتيجة غياب الخدمة ضمن النسخة المدققة؛ لا نفترض أن وجود نموذج كلمة مرور يحقق دخولًا حقيقيًا. كلمات المرور المؤقتة في MutableStateFlow ولا يحفظها المستودع. بيانات شاشة Auth الأخرى وبعض حالتها في SavedStateHandle؛ ينبغي مراجعتها مع سياسة مزود حقيقي.

المسارات القديمة محفوظة للتطوير وتجربة المعلم. تعطيل الديمو ليس بديلًا عن حراسة مستقبلية للجلسة المنتهية، وإعادة التحقق من account.stage، واسترجاع الإجراء المؤجل بعد المصادقة؛ `guarded` الحالي لا يحتفظ بطلب عودة كامل.

## 5. الهوية والزائر وثبات المرحلة

### المنفذ فعليًا

- `StudyStage { G9, BAC }` و`User.localId/studyStage/legacyWalletKey` في `core/model/Models.kt:29` وما بعدها.
- `LocalLearnerStore` ينشئ UUID، ويخزن الاسم والمرحلة وguest في registry. `LocalLearner.user()` ينتج Student أو Guest، **ولا يعني Student أنه authenticated**.
- ملف واحد للزائر لكل مرحلة: طلب BAC guest ثانية يختار UUID السابق، ولا يصفر تقدمه. يمكن وجود عدة ملفات طالب محلي وأسماء متطابقة بمعرفات مختلفة.
- `enmath_local_identities_v1` يحتوي registry وactive وjournals؛ snapshot شخصي في `enmath_learner_<UUID>` يحتوي owner وcompleted وlast وProductState.
- التفعيل يستعيد snapshot الشخصي ولا يضيف إليه بيانات صفوف المعلم المشتركة. آخر ملف active يرجع عند إنشاء المستودع.
- `LocalDemoRepository.update` يطابق User مع سجل هويته ويرفض تغيير المرحلة/الدور عبر copy؛ `signIn` للملف المحلي يتحقق من التطابق أيضًا.
- `LearningRules.commandOwner/acceptsCommand` وعمليات AppViewModel تمنع أوامر هوية سابقة من كتابة الإكمال/المحاولة/المحفوظات/السجل في ملف لاحق.
- التبديل يعيد Solver، وينظف مكدس التنقل المحفوظ عند تغير localId. QuizViewModel وInteractiveLessonViewModel مرتبطان بمالك العمل، ولهما منع تكرار الإنهاء.
- الخروج المحلي يلغي active ويزيل حالة المتعلم المعروضة، ويحافظ على ملفات تقدمه والجواهر التاريخية.

المراجع: `LocalLearnerStore.kt:11,26,68,74,87,103`، `LocalDemoRepository.kt:114,125,146,193,215,245`، `ProductRepository.kt:17`، `AppViewModel.kt:80`، `ENMathApp.kt:88,230`.

### الناقص أو المحدود

- لا AccountSession أو accountId موثّق أو SessionMode مستقل يميز المحلي عن السحابي. لا نسمي ملف الطالب المحلي «حسابًا حقيقيًا» في التنفيذ القادم.
- مرحلة الملف ثابتة برمجيًا؛ لا توجد ضمانة خادم لحساب لم يُنفذ بعد.
- لا curriculumEditionId، ومعظم Lesson/Question/Attempt/HistoryItem لا تحمل stage/owner/revision داخل السجل؛ الملكية الحالية ضمن ملف snapshot الخارجي.
- إعادة فتح ملف محلي لا تتطلب سرًا. العزل المنطقي ليس حماية خصوصية من مستخدم آخر للجهاز.
- لا ترقية Guest→Account ولا نقل محفظة تلقائي؛ إنشاء ملف طالب محلي بعد زائر ينتج UUID آخر، ولا يضم بيانات الزائر.
- إعداد اللغة والثيم عام للتطبيق في `enmath_demo`، بينما السجل والتقدم والمحاولات شخصية. هذا مناسب إن اعتمد كقرار واضح، ولا ينبغي تفسير مشاركة الثيم على أنها تسرب تقدم.

### أدلة وملاحظات محددة

1. `LearningState.books/practiceSets` يفرغان عندما G9 فقط؛ null stage يسقط إلى كتالوج البكالوريا. `questions/students/examples` تبقى مرتبطة بـ ProductSeed/DemoContent. المرجع `LearningRepository.kt:24–43`؛ لا ينبغي تحويله إلى ضمان stage شامل.
2. `ProductGraphs.kt:61–155` يحمي Home/Study/Books/Topic/Lesson/Practice/result للتاسع. بقية routes مشتركة. روابط التنقل الداخلية ذات id عابر لا تحمل stage؛ يجب التحقق من الكتالوج المسموح عند كل قراءة وأمر، لا الثقة بمقطع route.
3. `StudentHomeV2.kt:119` يبني قائمة journeyNodes ثابتة، و`:784` تقريبًا يصنف غير المكتمل وغير الحالي LOCKED مع استثناء `index == 2 && completedSet.size >= 2`. القفل من حالة الواجهة وليس سياسة توفر درس؛ قد يمنع درسًا موجودًا أو يوحي بأن درسًا ناقصًا جاهز.
4. Home الحالية للبكالوريا رحلة متعرجة، وليست Home البكالوريا المقترحة بأولوية الاستمرار/الخطة/الكتابين. لا يُعاد استعمالها كتاسع قبل فصل بيانات المرحلة وتوثيق تصميمها؛ ذلك سيعرض أسماء دروس بكالوريا للتاسع.
5. `CurriculumScreen.kt:102,209,239` تحسب الإكمال من state، لكن أسماء الموضوعات وملخصاتها وchips ثابتة. «الأعداد المركبة» مربوط بـ `logarithms`، بينما محتواه الفعلي في ProductSeed عن ln؛ هذا عدم تطابق مؤكد يجب تصحيحه من المصدر المعتمد، لا إخفاؤه بتغيير النسبة.
6. `StudentLimitsTopic` يعيد استخدام عرض النهايات لموضوعات أخرى مع بدائل ثابتة؛ يحتاج تقديمًا معتمدًا على نوع المحتوى، لا قوالب توحي بدروس غير مكتملة.
7. `CourseScreens.kt` يعالج book id المجهول بحالة فارغة. `StudentHomeScreen.kt:18` القديمة تفترض `books.first()`، وتوجد واجهات Legacy/BeforeApproved/Reference؛ ليست Home الحالية في graph، لكنها خطر عند إعادة ربطها بكتالوج تاسع فارغ. لا حذف لها ضمن هذا العمل.
8. `LearningRules.stats` لا يستعير seeded accuracy لملف UUID جديد، وهذه نقطة تحسن. لكن fallbacks تجريبية باقية للمسارات القديمة. فصل الإكمال عن الإتقان موجود جزئيًا في `CurriculumPresentation.kt` ويستحق الحفاظ.
9. Solver يستخدم `DemoSolverEngine` ويصرح بأمثلة بكالوريا منتقاة؛ Graph يستخدم `DemoGraphEngine`. لا يصح تسويق أي منهما كمحلل عام أو منهج تاسع كامل. حالة SolverHistory محفوظة شخصيًا، لكن ExploreScreen لا يتلقى سياق المرحلة في graph.
10. Library مكتبة محفوظات/موارد محلية، وليست مدير تنزيل كتب/PDF. جرد assets أظهر KaTeX وأوراق جواهر نصية، ولم يظهر كتب تاسع أو فيزياء PDF مع حقوق نشر. لا دليل على تنزيل حقيقي/استئنافه/فحص سلامة ملف.
11. ProfileHero يبين مرحلة الطالب، لكن وصف الدور غير المعلم يستخدم «طالب» حتى مع Guest. مطلوب تمييز «زائر التاسع/زائر البكالوريا» صراحة عبر النقاط الأكاديمية.

## 7. التخزين والجواهر والترحيل

### مخازن البيانات الحالية

| المخزن | محتواه/المالك | الضمان الحالي والحد |
|---|---|---|
| `enmath_demo` SharedPreferences | إعدادات عامة وجلسات/بيانات Legacy وصفوف المعلم | باقٍ للتوافق؛ لا يجوز clear أو إعادة seed لإصلاح مشكلة |
| `enmath_personal_<SHA256(owner)>` | نطاقات Legacy مرتبطة بهوية قديمة | تستخدم للتوافق/الاستيراد؛ لا تحول الاسم أو البريد إلى UUID جديد تلقائيًا |
| `enmath_local_identities_v1` | registry profiles/active/journals | إصدار 1، تحقق UUID والتكرار ومفاتيح محافظ الطلاب ومراحل الزائر |

| `enmath_local_gems_v1.db` | 6 جداول حساب/مكافآت/استثناءات/فتح/دروس/تقييمات | SQLite معاملات ومفاتيح owner؛ ليست Room أو محفظة سحابية |

`ProductCodec` يرمي CorruptLocalData عند JSON غير صالح بدل إبداله تلقائيًا بـ seed. `LocalLearnerStore.save` لا يستبدل snapshot تالفًا/غير مدعوم. فشل commit يمنع إعلان نجاح العملية؛ توجد حالة تخزين وتعليمات بعدم مسح البيانات. كتابات JSON للهوية والتعلم متزامنة؛ الحجم المتزايد قد يحتاج نقلًا إلى IO ومخزن قابل للفهرسة مستقبلًا، دون إعادة كتابة متسرعة.

### ما هو حقيقي في الجواهر؟

- `LocalGemsPolicy.owner`: Student فقط؛ المفتاح legacyWalletKey إن وجد، وإلا localId، وإلا بريد الديمو القديم. Guest وTeacher لا يحصلان على مالك مكافآت.
- محفظة فعلية محلية، ledger ومفاتيح مكافآت فريدة `(owner,achievement)` وعمليات فتح لا تتكرر، وحدود يومية 40 وأسبوعية 120.
- إكمال درس يدوي لا يكفي للجواهر؛ يحتاج checkpoint صحيحًا أو تحقق درس تفاعلي. التدريب المؤهل يحتاج إجابات وعتبة 80%. المبالغ من ledger وليست أرقام remember تجميلية.
- الملف UUID يسجل الأمر والتعلم وpendingGemEvents في snapshot واحد؛ `deliver` يكتب ledger ثم يقر الحدث. إعادة الحدث لا تضاعف المكافأة، والمستخدم المتغير لا يستقبل إشعار محفظة سابقة.
- استبعاد مكافآت البيانات السابقة وتجنب المنح الرجعي موجودان. نوعا WEEKLY/MASTERY باقيان لقراءة التاريخ، لكن السياسة تمنع صك مكافآت جديدة منهما.
- `SQLiteLocalGems` يعطل الحذف التلقائي عند تلف DB، وonUpgrade يرفض الإصدار غير المدعوم بدل DROP. يلزم migration إضافي قبل رفع version؛ الرفض يحفظ الأصل لكنه ليس استعادة تلقائية.

المراجع: `LocalGemsPolicy.kt:31,41,62`، `LocalLearningGems.kt`، `LocalGemsCoordinator.kt:26,64,116`، `SQLiteLocalGems.kt:12,56`، `assets/local_gems/schema.sql`، `AppViewModel.kt:57,64,98,154`.

### مخاطر يجب حسمها قبل توسيع التجربة

- **مرحلة البيانات المهاجرة:** `LocalLearnerStore.migrate/resumeMigrations:142,157` ينسخان completed/last/attempts/history وغيرها إلى المرحلة المختارة بلا تدقيق مطابقة المحتوى. اختبار `migrationResumesAfterPreparedJournalWithoutClaimingTwice` يختار G9 لمصدر يحوي `limits-practice` ويحتفظ بالمحاولات. هذا يثبت الحفظ لكنه لا يثبت صحة المرحلة. تبقى البيانات محفوظة ومعلّقة عند التعارض؛ لا نحذف أو ننسب آليًا. تأكيد المستخدم ليس إثباتًا خادميًا للهوية.
- **المحفظة القديمة:** الاستيراد يحتفظ بمفتاح email القديم عمدًا ولا يعيد ترقيم SQLite. أي تحويل UUID شامل قد يظهر رصيدًا صفريًا ظاهريًا أو يكرر المكافآت أو يقطع الاستحقاقات. يلزم alias mapping موثّق مع تحقق الرصيد والتاريخ والفتح؛ لا «إصلاح» عبر إنشاء محفظة بديلة ثم حذف الأصل.
- **بيانات المعلم:** الاستيراد يستبعد classes/assignments/submissions/resources/questions/notifications من النسخة الشخصية لغياب UUID provenance، ويبقيها في المصدر. هذا يحافظ على المصدر، لكنه يعني أن الملف المستورد لا يملك تجربة الصفوف السابقة تلقائيًا. لا تعالج الفجوة بنسخ صفوف المعلم أو تعديل IDs الخاصة بها.
- **أكثر من مخزن:** registry وsnapshot وDB ليست معاملة SQLite واحدة. مسار UUID لديه outbox وjournal جيدان؛ المسار Legacy ما يزال عدة كتابات متتالية مع احتمالات انقطاع بينها. لا ادعاء atomicity شاملة لكل المسارات.
- **حراسة المستوى الأدنى:** `LocalDemoRepository.completeLesson/openLesson:228,233` تستخدم DemoContent مباشرة، مقابل AppViewModel الذي يفحص state.lesson. الواجهة الحالية تحمي G9، لكن استدعاء raw repository من نقطة جديدة قد يتجاوز المرحلة. يحتاج عقد stage/content في طبقة الأوامر، دون الادعاء بوجود استغلال UI مثبت الآن.
- **متجر الجواهر:** `LocalGemCatalog` بلا stage ويعرض أوراق نهايات/اشتقاق/تكامل، وwallet route عامة. حتى ملف G9 قد يرى كتالوج إثراء بكالوريا؛ يجب فحص المرحلة عند listing/purchase/openContent مع الحفاظ على unlocks القديمة. منع كسب الجواهر للزائر لا يعالج تصنيف المحتوى.
- **الاستعادة:** `allowBackup=false` ولا خدمة مزامنة/تصدير موثقة. حفظ الجهاز لا يعني استردادًا بعد حذف التطبيق أو فقد الجهاز. يجب أن تبقى الرسائل صريحة، مع تصميم استعادة آمنة لاحقًا إذا اعتمدت.

## 8. معمارية تجربتين دون تكرار المنطق

**القرار المقترح: Shared domain + presentation لكل مرحلة، داخل module التطبيق الحالي أولًا.** لا حاجة لنسخ AppViewModel أو LocalLearnerStore أو ledger أو محرك التصحيح.

```text
هوية محلية محفوظة / جلسة حساب مستقبلية
                 ↓ سياق موثوق: owner + stage + curriculum edition
Catalog / Learning / Progress / Planner / Gems / Resources
                 ↓ StudentUiState وبيانات فعلية/حالة فارغة
StageStudentScaffold + StageUiSpec
       ├─ Grade9Home / Grade9Catalog / Grade9LessonPresentation
       └─ BacHome / BacCatalog / BacLessonPresentation
                 ↓
مكونات مشتركة: أزرار، حالات، بطاقات تقدم، Math، نماذج، RTL، tokens
```

- `StageUiSpec` يحدد الترتيب والكثافة والعناوين وCTA وطريقة تقديم المحتوى. لا يمنح جواهر ولا يقرر ملكية أو صحة إجابة.
- Stage من الهوية الموثقة، وليس route argument أو chip قابل للتغيير أثناء الجلسة. unknown stage حالة معالجة صريحة، لا fallback إلى BAC.
- `ContentCatalog` يرجع مواد المرحلة وإصدارها وحقوقها وحالات التوفر. نقل استدعاءات Seed المباشرة تدريجيًا مع adapter يحفظ IDs القديمة.
- اختلاف Home: التاسع خطوة تالية/هدف أسبوع/مسار واضح؛ البكالوريا استمرار/الكتابان/مراجعة/خطة. lesson renderer وassessment commands مشتركة، مع ترتيب وأمثلة ملائمة للمادة الفعلية.
- استخراج Student repositories أو use cases تدريجيًا من LearningRepository/AppViewModel الكبير؛ teacherGraph وTeacherWorkspace ومخازن الصفوف تبقى تحت عقدها القائم.
- إعادة استخدام Theme/ExperienceTokens/ResourceBaseline وMathRender/NativeEquations؛ لا نسخ palettes متنافسة في كل شاشة. لكل route مشترك مواصفة اختلاف مقبولة أو سبب اشتراك موثق.

## 11. خطة التنفيذ المقترحة وبوابات القبول

### الدفعة 0 — تثبيت خط الأساس، اكتملت تحليليًا

هذا التقرير وجرد Working Tree وحدود الديمو ونتيجة اختبارات JVM. قبل أي تنفيذ لاحق: حفظ نسخة قابلة للاسترجاع من حالة العمل الحالية دون Commit/Push غير مصرح، وتجهيز fixtures ترقية معزولة تمثل المخازن الحالية. لا تنفّذ نسخة/ترحيل على بيانات جهاز طالب أثناء التطوير.

### الدفعة 1 — مواصفات UX وعقود البيانات، قبل البرمجة

رسم ومراجعة E01–E12 مع بديل محلي صريح إذا لم تتوفر الحسابات، وHome/Courses/Lesson/Planner للمرحلتين؛ Light/Dark وحالات Empty/Error/Offline/WrongStage. تحديد ترتيب sections وقبول فرق بصري فعلي، وخريطة route→presentation. بالتوازي تصميم owner/stage/edition وmapping Legacy وحالات تعارضه، دون تغيير أي بيانات.

**البوابة:** اعتماد مخطط الرحلتين ومراجعة عقد الترحيل. لا تُنشأ شاشات حسابات توحي بأن خدمة غير موجودة جاهزة.

### الدفعة 2 — حماية الهوية والمحتوى والترحيل P0

توسيع الأساس الموجود بدل استبداله: تمييز نوع الجلسة، فحص stage/catalog في repository/use cases، مراجعة مصدر كل سجل مهاجر، aliases للمحافظ القديمة، بقاء البيانات المجهولة محفوظة. توثيق ما يحدث عند فشل كتابة snapshot/registry/DB وعند الاستئناف. لا تخمين مرحلة من الاسم أو البريد أو أول درس فقط.

**البوابة:** restart/crash/replay/wrong-stage/duplicate migration لا تفقد سجلًا أو تضاعف منحة؛ مطابقة الرصيد والفتح قبل/بعد؛ لا تغير مخازن المعلم.

### الدفعة 3 — رحلة البداية والزائر P1

ChooseStage ثم entry متخصصة، الزائر فعل أساسي، notice محفوظ، استعادة آخر هوية، تبديل مساحة مع حفظ السابقة، تنظيف حالة العرض والمكدس. توحيد legacy routes مع المدخل المحلي دون كسر tags أو تجربة المعلم. لا login إنتاجي ناجح حتى الدفعة الخاصة بالمزود.

**البوابة:** أول تشغيل offline، BAC guest ثم G9 guest ثم العودة، UUID ثابت وتقدم منفصل؛ الرجوع لا يكرر ملفًا أو يعيد فتح بيانات غير مختارة.

### الدفعة 4 — كتالوج صحيح وأول دورة تعلم لكل مرحلة P0/P1

اعتماد مصادر المنهج وحقوق الموارد وإصدارها، وضع adapter يحفظ معرفات الكتالوج القديم، ومراجعة العناوين والـ checkpoints والـ rubrics. مادة حقيقية واحدة على الأقل لكل مرحلة متى توفرت: درس→إجابة→محاولة→نتيجة→تقدم بعد الإغلاق. إن لم تتوفر المادة يبقى Empty واضحًا؛ لا seed نجاح.

**البوابة:** لا chip أو node لدرس غير موجود، لا مثال مرحلة أخرى، ولا إتقان مستنتج من مجرد ضغط «مكتمل».

### الدفعة 5 — تجربتا العرض والصفحات المشتركة P1

Grade9 Home/Courses ومسار تربوي، Bac Home باستمرار وكتابين وأولوية مراجعة. renderer مشترك يعرض محتوى مختلفًا حقيقيًا؛ stage في header/profile ومداخل الدراسة. تصحيح الأقفال، ضبط Solver/Graph/Library/متجر الجواهر، وتوثيق ما يبقى مشتركًا لكل route. تحترم الحالات القديمة والـ unlocks؛ لا إخفاء التاريخ على أنه حذف.

**البوابة:** قبول مستقل للتصميمين، بيانات الطالب مصدر كل بطاقة، regression للملاحة والمعلم والتعلم والجواهر.

### الدفعة 6 — Planner والمراجعة والموارد المحفوظة P1

نماذج أهداف وخطة وتاريخ وحمل مهام متبقية، والمراجعة المبنية على إجابات حقيقية. حفظ offline ضمن owner/stage؛ سياسة وقت أسبوع موحدة مع Asia/Damascus بدل خلط أيام UTC في النشاط مع أيام الجواهر المحلية. تنزيل/PDF فقط بعد توفر مادة وحقوق وتحقق ملفات فعلي.

**البوابة:** إغلاق وإعادة تشغيل يعيدان خطة الزائر/الطالب الصحيحة؛ لا يظهر نشاط أو هدف من ملف آخر؛ لا مكافآت رجعية.

### الدفعة 7 — Auth الحقيقي المشروط P2 زمنيًا، إلزامي قبل تسويق حسابات

حسم مزود يدعم وسيلة دخول/إثبات/استعادة قابلة للاختبار في سوريا، وسياسة رقم واحد لمرحلتين. Account.stage ثابت لدى المصدر الموثوق، معالجة اختلاف المرحلة قبل دخول الحساب، انتهاء الجلسة، أخطاء الشبكة، عدم حفظ كلمة المرور، ومراجعة claim بيانات زائر من نفس المرحلة مع idempotency وتعارضات معلنة.

**البوابة:** إنشاء/دخول/استعادة حقيقية على خدمة فعلية، فشل الشبكة لا ينتج نجاحًا، ولا تغيير stage أو merge صامت. إن لم يعتمد المزود يبقى الإصدار معلنًا كتعلّم محلي؛ يمكن إعداد بنية الجلسة مبكرًا دون ادعاء جاهزية الخدمة.

### الدفعة 8 — قبول QA وإطلاق لاحق

اختبارات JVM وSQLite للهجرة والملكية ومنع التكرار، ثم جهاز فعلي بإدارة المستخدم للترقية والرجوع وprocess death وLight/Dark وRTL/LTR وMath LTR وfont 200% وTalkBack/IME/48dp. قبول التصميمين لا يُستنتج من نجاح unit tests. لا Emulator/ADB أو Commit/Push إلا وفق تعليمات المستخدم؛ هذه الجولة لم تستعملها.

## 12. التحقق المنجز وحدود النتيجة

### ما شُغّل

أُجريت قراءة المصادر والبحث عن النماذج/Routes/SDKs وقراءة اختبارات التخزين. أول محاولة Gradle باستعمال JBR الموجود مع Android Studio توقفت قبل الاختبارات برسالة `25.0.3`. جرى استخدام JDK 21 الموجود والمحدد في `.gradle/config.properties`، دون تعديل إعدادات المشروع.

```powershell
$env:JAVA_HOME = '<LOCAL_USER_RESOURCE>'
.\gradlew.bat :app:testDebugUnitTest --offline --console=plain
.\gradlew.bat :app:testDebugUnitTest --rerun --offline --console=plain
```

الأول ناجح مع task محدثة مسبقًا؛ الثاني **أعاد تنفيذ test task فعليًا**. نتيجة XML: **23 suite / 188 اختبارًا / 0 failures / 0 errors / 0 skipped**. المخرجات في `app/build/test-results/testDebugUnitTest/` و`app/build/reports/tests/testDebugUnitTest/`. لم تُضف اختبارات جديدة، ولم تُنشأ بيانات داخل التطبيق؛ fixtures الاختبارات مؤقتة ومعزولة.

تغطية مختارة أُعيد تشغيلها: W1CompletionIdentityTest **19**، W1IdentityIsolationTest **7**، W1AuthBoundaryTest **3**، W1ProductRecoveryTest **6**، LocalGemsCoordinatorTest **13**، LocalGemsPolicyTest **28**، GemsIntegrationReviewTest **9**، ProfileGemsPresentationTest **6**. لا يثبت مجموع نجاحها صحة المنهج أو اكتمال UX.

السكربت الموجود `tools/test_local_gems_sqlite.py` يفحص schema الحقيقي على SQLite مضيف مع قواعد مؤقتة. **لم يُنفذ بنجاح**: `python` غير متاح و`py` غير معرف في PATH. لم يُثبت runtime أو يُغيّر الجهاز لهذا الغرض، ولا تُحسب اختبارات SQL نجاحًا في هذه الجولة.

## 13. قرارات مطلوبة عند الانتقال من التدقيق

1. اعتماد إطلاق تعلم محلي أولًا أم اشتراط Auth سحابي للإطلاق العام، مع تسمية واضحة للملف المحلي.
2. مصادر منهج التاسع والبكالوريا وإصداراتها وحقوق المواد والفيزياء؛ لا اعتماد عناوين الكتالوج الحالي كفهرس رسمي.
3. سياسة مراجعة Legacy مجهول المرحلة/الملكية، والحفاظ على alias المحفظة؛ لا ترحيل صامت أو حذف.
4. اعتماد مواصفات اختلاف Home/Courses/Lesson/Planner للمرحلتين، وتسميات الزائر ومسار تبديل ملفاته.
5. قبل Auth: المزود والهوية الفريدة واستعادة رقم واحد لحسابين وسياسة تعارض ترقية الزائر.

**حكم الجاهزية:** أساس التعلم المحلي والعزل والجواهر قابل للبناء عليه، مع اختبارات ناجحة وتحسينات يجب صونها. متطلبات التجربتين والمصادقة الحقيقية والمحتوى المعتمد والخطة لم تكتمل. انتهت هذه الجولة عند التدقيق وكتابة التقرير، دون بدء برمجة التنفيذ.
